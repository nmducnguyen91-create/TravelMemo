# ADR-003 — Optional multi-device sync through Firebase (owner request 2026-11-27)

**Decision.** Add opt-in sync between the owner's devices using Firebase Authentication (Google sign-in) and Cloud
Firestore on the free Spark plan. Project: `travelmemo-ce0d6`, Firestore `(default)` in `asia-southeast1` (Singapore),
production-mode rules. Analytics and Gemini were turned off at project creation.

**Why.** Owner asked to keep data in step across phone and computer. This amends the MVP "no backend / no account /
no automatic upload" rule only for owners who switch sync on; the default remains fully local.

**Design.**
- SQLite stays authoritative on every device. The cloud is a relay of row changes, not the source of truth.
- Change tracking is off until the owner turns sync on. Then the engine installs SQLite triggers that write
  `(table, primary key, change time)` into `sync_outbox` (migration 0004). Existing rows are queued once with change time
  1970-01-01 so any real edit on another device wins over them.
- Remote layout: `users/{uid}/rows/{table~key}` = `{ t, k, d (row or null for delete), u (change time), dev, s (server time), v (schema) }`.
- A round = pull (documents with `s` ≥ cursor − 5 min), apply in one transaction with triggers muted and foreign keys
  deferred, then push the outbox in batches of 400. Conflicts: last writer wins per row by change time, ties by device id.
- Rows whose parent is missing are parked in `sync_parked` and retried on every pull. Columns unknown to the running
  app version are ignored; tables outside the list are refused.
- Synced: profiles, companions, places, trips, trip_companions, visits, visit_regions, passports, passport_stamps,
  media_assets (metadata only), journal_entries. Device-local: geography, stamp templates, settings, backup history.
- `firestore.rules` lets only the signed-in owner read/write their own rows, validates shape and table names, and closes
  everything else.
- No network request is made until sync has been turned on once on that device.
- Web config comes from `EXPO_PUBLIC_FIREBASE_*` at build time (`.env.local`, or repository variables in the Pages
  workflow). These identify the project and are not secrets; access control is the rules.

**Limits / follow-ups.**
- Photo bytes are not synced: Cloud Storage for new buckets needs the paid Blaze plan. Thumbnails could be stored in
  Firestore (<1 MiB per document) as a later step.
- Clock skew between devices can make an older edit win; acceptable for a single owner.
- Live Google sign-in could not be exercised from the cloud build environment (its proxy blocks apis.google.com);
  needs a check on a hosted HTTPS build.
- Spark quotas: 50k reads / 20k writes / 1 GiB per day-project; ample for one owner.
